## 1. 進め方テンプレ（60 分の使い方）

面接官は「正解」ではなく「曖昧な要件をどう切り分け、なぜその部品を選んだか」を見る。
時間配分の目安：

1. **要件の明確化（5–8 分）** ―― ここを飛ばすと減点される。必ず質問してから描く
   - 機能要件：誰が・何を・どの端末で。「最初のリリースで必須なのはどれですか？」
   - 非機能要件：ユーザー数・同時接続・DAU、レイテンシ目標、可用性、一貫性の強さ、データ保持期間
   - 制約：既存システムの有無、予算、チーム規模、クラウド前提か
2. **見積もり（3–5 分）** ―― 桁だけで良い。QPS・ストレージ・帯域を口頭で
3. **ハイレベル構成図（10 分）** ―― クライアント → CDN/LB → API → サービス → DB/キャッシュ/MQ。まず"動く最小構成"を描く
4. **データモデル & API（10 分）** ―― 主要テーブル 3–5 個、主キー・インデックス・外部キー。REST の主要エンドポイント 3–5 本
5. **深掘り（15–20 分）** ―― 面接官が興味を示した箇所を掘る。ボトルネック → 解決策 → そのトレードオフ、の順で必ず 3 点セットで話す
6. **信頼性・運用（5 分）** ―― 障害時の挙動、監視、デプロイ、バックアップ
7. **まとめ（2 分）** ―― 「今の設計の一番の弱点は X で、規模が 10 倍になったら Y を入れます」

鉄則
- 部品を出すときは必ず「なぜ必要か → 代替案 → 選んだ理由」をワンセットで
- 「分からない」より「仮定を置いて進めます。例えば DAU 100 万と仮定して……」
- 面接官の質問は方向転換のヒント。素直に乗る

## 2. 部品別トレードオフ早見表（面接で口にする "理由" 付き）

### 2.1 データベース
| 選択 | 使う場面 | 言うべきトレードオフ |
|---|---|---|
| RDB（MySQL/PostgreSQL） | 取引・ユーザー・権限など整合性が要る中核データ | ACID・JOIN・制約が強い。書き込みスケールは垂直分割かシャーディングが必要 |
| NoSQL KV/Doc（DynamoDB/MongoDB） | 学習履歴・イベントログ・スキーマが変わりやすいもの | 水平スケールが容易、結果整合。JOIN 不可、トランザクションが弱い |
| 列指向/DWH（BigQuery/Redshift） | 分析・集計・ダッシュボード | 大量スキャンに強い、点更新に弱い、遅延数秒〜分 |
| 時系列 DB | メトリクス・センサー | 圧縮率と時間範囲クエリに強い |

必ず言う 3 語：**インデックス**（読み速く書き遅く）、**レプリケーション**（読み分散・可用性・レプリカ遅延）、**シャーディング**（書き分散・キー選定が命・クロスシャード JOIN が痛い）。

正規化 vs 非正規化：更新頻度が高ければ正規化、読みが圧倒的に多ければ非正規化（＋整合性を誰が守るか言う）。

### 2.2 キャッシュ
- どこに：クライアント / CDN / API 側（Redis, Memcached）/ DB 内部
- 戦略：Cache-aside（一般的、ミス時 DB へ）、Write-through（整合性優先）、Write-back（書き込み高速だが消失リスク）
- 言うべきリスク：**キャッシュ無効化**（TTL か明示削除）、**Thundering herd**（同時ミス→ロック/早期再計算）、**ホットキー**（複製・ローカルキャッシュ）
- Redis の追加用途：セッション、レート制限、ランキング（Sorted Set）、分散ロック

### 2.3 メッセージキュー / 非同期
- 用途：ピーク平準化、疎結合、リトライ、ファンアウト（1 イベント→複数消費者）
- 選択：SQS（シンプル・順序弱い）、Kafka（高スループット・順序保証はパーティション内・再読可）、RabbitMQ（ルーティング柔軟）
- 言うべき設計点：**at-least-once → 冪等性**（処理 ID で重複排除）、**DLQ**、**順序が要るならパーティションキー**、**バックプレッシャー**

### 2.4 API 設計
- REST：リソース指向、キャッシュしやすい、公開 API 向き
- gRPC：内部サービス間、型安全・高速・ストリーミング。ブラウザ直は不向き
- GraphQL：画面ごとに必要な形が違うとき。N+1 と複雑度制御が課題
- ページネーションはカーソル方式、冪等キー、バージョニング、レート制限を一言添える

### 2.5 スケーラビリティの型
- ステートレス API + LB → 水平スケール。セッションは Redis へ
- 読み：レプリカ + キャッシュ + CDN
- 書き：キュー + シャーディング + バッチ化
- 重い処理：ワーカー分離（非同期ジョブ）
- スパイク：オートスケール + キュー + 事前ウォームアップ（Monoxer なら「授業開始時刻・宿題締切前」が典型スパイク）

### 2.6 信頼性・一貫性
- CAP/PACELC：ネットワーク分断時に C か A か。「学習履歴は A 優先で結果整合、課金・成績確定は C 優先」のように用途で分ける
- 冗長化：マルチ AZ、ヘルスチェック、フェイルオーバー、サーキットブレーカー、タイムアウト+リトライ（指数バックオフ+ジッター）
- 観測性：メトリクス（RED: Rate/Error/Duration）、ログ、トレース、SLO とアラート

### 2.7 モバイル/教育系で出やすい追加論点
- **オフライン対応**：端末ローカル DB（SQLite）に学習記録を溜めて同期。競合は「サーバー時刻 + 端末生成 UUID」で解決
- **プッシュ通知**：APNs/FCM、トークン管理、バッチ送信、配信時刻の分散
- **個人情報（未成年）**：学校単位のテナント分離、権限（生徒/保護者/教師/学校管理者）、監査ログ、暗号化
- **マルチテナント**：DB を共有しつつ tenant_id を全テーブルに + Row-Level Security、または大口校は専用シャード

## 3. 数字カンニングペーパー（桁だけ覚える）

**Latency numbers（Jeff Dean 版・概算）**
| 操作 | 時間 |
|---|---|
| L1 キャッシュ参照 | 1 ns |
| L2 キャッシュ参照 | 4 ns |
| メインメモリ参照 | 100 ns |
| SSD ランダム読み | 100 µs |
| 同一 DC 内ネットワーク往復 | 0.5 ms |
| HDD シーク | 10 ms |
| 1 MB をメモリから逐次読み | 0.25 ms |
| 1 MB を SSD から逐次読み | 1 ms |
| 東京 ↔ 米西海岸 往復 | 100 ms 前後 |

**見積もりの定番**
- 1 日 ≈ 86,400 秒 ≈ 約 10^5 秒。「DAU 100 万・1 人 50 リクエスト/日 → 5×10^7/日 → 平均 約 600 QPS、ピークは 5–10 倍で 3,000–6,000 QPS」
- 1 レコード 1 KB × 1 億件 = 100 GB
- 単一 RDB の目安：数千 QPS の書き込み、数万 QPS の読み（キャッシュ併用で）
- Redis：単一ノードで 10 万 QPS 級
- Kafka：パーティション増やせば 100 万 msg/s 級

**可用性**
- 99.9% = 月 約 43 分停止、99.99% = 月 約 4 分

## 4. 例題 3 本（Monoxer を想定した練習）

### 例題 A：「Monoxer のような記憶定着アプリのバックエンドを設計してください」

**明確化の質問例**
- 生徒 / 教師 / 学校管理者 の 3 ロールで良いか
- 規模：導入校 数百〜数千校、生徒 数十万〜数百万、授業時間帯に集中アクセス
- 主要機能：課題（Book/Task）の配信、問題出題、解答記録、忘却曲線に基づく次回出題日の計算、教師向け進捗ダッシュボード
- オフライン学習の要否、通知の要否

**見積もり**
- 生徒 100 万、1 人 1 日 100 問 → 10^8 解答/日 → 平均 約 1,200 QPS、授業帯ピーク 10 倍で 1 万 QPS 超の書き込み
- 1 解答レコード 200 B → 20 GB/日、1 年で 7 TB → 学習履歴は追記専用・パーティション分割が前提

**ハイレベル構成**
- クライアント（iOS/Android/Web）→ CDN（静的・音声・画像）→ API Gateway/LB → API（ステートレス）
- コア DB（RDB）：学校・クラス・ユーザー・課題・問題（マスタ、整合性重視）
- 学習履歴（書き込み集中）：API → MQ（Kafka/SQS）→ ワーカー → 追記型ストア（時系列パーティションの RDB か DynamoDB）
- 次回出題スケジュール：Redis に「生徒 × 問題 → 次回期日」を保持（Sorted Set で期日順取り出し）＋ 永続化は DB
- 教師ダッシュボード：DWH（BigQuery）に日次/準リアルタイムで流し、集計は事前計算（マテリアライズドビュー）

**データモデル（最低限）**
- schools(id, name, plan) / classes(id, school_id) / users(id, role, school_id) / enrollments(user_id, class_id)
- books(id, owner_school_id) / questions(id, book_id, type, payload_json) / assignments(id, class_id, book_id, due_at)
- answers(id, user_id, question_id, answered_at, correct, latency_ms) ―― パーティション：answered_at 月次 ＋ user_id ハッシュ
- memory_states(user_id, question_id, strength, next_due_at) ―― 主キー (user_id, question_id)、next_due_at にインデックス

**深掘りで話すトレードオフ**
- 解答を同期で DB に書くか、MQ で非同期にするか → UX 上「保存しました」は即返したい。API はキュー投入で 200 を返し、クライアントは楽観的更新。失敗時はリトライ + 冪等キー（client_answer_id）
- 忘却曲線計算をリアルタイムで行うか → 出題時に計算して Redis に置く。バッチで夜間再計算
- オフライン同期の競合 → 端末側で UUID 生成、サーバーはタイムスタンプ順にマージ、同一問題の重複は最後の解答を採用
- マルチテナント分離 → tenant_id 列＋アプリ層での強制、大規模塾は専用 DB へ移行可能な設計
- ピーク → 授業帯を予測してオートスケール、キューで吸収。教師ダッシュボードは数分遅延を許容と明言

### 例題 B：「毎朝 8 時に全生徒へ "今日の課題" 通知を送るシステム」

- 要件：数百万通を 8:00 ± 数分で。重複禁止、失敗リトライ、配信率の可視化
- 構成：スケジューラ（cron/Cloud Scheduler）→ 「対象抽出ジョブ」が user_id を 1 万件ずつチャンクにして MQ へ → ワーカー群が FCM/APNs に並列送信 → 結果を結果テーブルに記録
- トレードオフ：時刻を分散（7:55–8:05）して API レート制限を回避 vs "8 時ちょうど" の期待。冪等性は (user_id, date) をキーに送信済みを Redis SETNX で確認
- 障害：ワーカー落ち → MQ の可視性タイムアウトで再配信。FCM 障害 → サーキットブレーカー + DLQ で後追い

### 例題 C：「LLM で問題を自動生成し、教師がレビューして配信するパイプライン」（あなたの強みに寄せる）

- 要件：教材テキスト（PDF）→ 問題候補生成 → 品質チェック → 教師レビュー → 配信。コスト・レイテンシ・品質
- 構成：アップロード → OCR/構造化 → チャンク化 → ジョブキュー → 生成ワーカー（LLM API、レート制限管理）→ 自動評価（ルール + LLM-as-a-Judge）→ レビュー UI → 承認で questions テーブルへ
- トレードオフ：同期 vs 非同期（数分かかるので必ず非同期 + 進捗通知）、キャッシュ（同一教材の再生成を防ぐ：入力ハッシュ）、コスト制御（バッチ API、モデル使い分け）、幻覚対策（出典チャンクを必ず添付・人間承認を必須に）
- ここは SoftBank での RAG・評価・文書構造化の実務経験を具体的に引用する

## 5. 「ハードウェア寄り」の質問に備える（過去の受験者談）

短く答えられれば十分。
- CPU キャッシュとメモリ階層：L1/L2/L3 → RAM → SSD → HDD。局所性が大事、配列走査が連結リストより速い理由
- SSD と HDD：ランダム I/O の差 100 倍。DB のインデックス設計や WAL（追記）が有利な理由
- ネットワーク：RTT が支配的。往復回数を減らす（バッチ、コネクション再利用、HTTP/2）
- スレッドとプロセス、コンテキストスイッチ、I/O バウンドなら非同期、CPU バウンドならマルチプロセス
- 並行処理：ロック・競合状態・デッドロック、楽観ロック vs 悲観ロック、冪等性で "リトライ安全" にする
