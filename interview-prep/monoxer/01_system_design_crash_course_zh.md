## 1. 流程模板（60 分钟怎么分配）

面试官看的不是"标准答案"，而是你怎么拆解模糊需求、为什么选这个组件。
时间分配参考：

1. **澄清需求（5–8 分钟）** —— 跳过这步会扣分。一定先提问再画图
   - 功能需求：谁用、做什么、什么终端。"第一版必须有哪些功能？"
   - 非功能需求：用户数、并发、DAU、延迟目标、可用性、一致性强弱、数据保留期
   - 约束：有没有现有系统、预算、团队规模、是否云上
2. **估算（3–5 分钟）** —— 只要数量级。口头说 QPS、存储、带宽
3. **高层架构图（10 分钟）** —— 客户端 → CDN/LB → API → 服务 → DB/缓存/MQ。先画"能跑的最小结构"
4. **数据模型 & API（10 分钟）** —— 主要表 3–5 张，主键、索引、外键。REST 主要端点 3–5 个
5. **深挖（15–20 分钟）** —— 顺着面试官感兴趣的点挖。永远按"瓶颈 → 解法 → 该解法的代价"三件套说
6. **可靠性与运维（5 分钟）** —— 故障时的行为、监控、部署、备份
7. **收尾（2 分钟）** —— "现在这个设计最大的弱点是 X，规模涨 10 倍我会加 Y"

铁律
- 每提出一个组件，必须配套说"为什么需要 → 备选方案 → 为什么选它"
- 不要说"不知道"，说"我先做个假设，比如假设 DAU 100 万……"
- 面试官的追问是换方向的提示，顺着走

## 2. 组件权衡速查表（附面试时该说的"理由"）

### 2.1 数据库
| 选择 | 适用场景 | 该说的权衡 |
|---|---|---|
| 关系型（MySQL/PostgreSQL） | 交易、用户、权限等需要强一致的核心数据 | ACID、JOIN、约束强。写入扩展要靠垂直拆分或分片 |
| NoSQL KV/文档（DynamoDB/MongoDB） | 学习记录、事件日志、schema 常变的数据 | 水平扩展容易、最终一致。不能 JOIN，事务弱 |
| 列存/数仓（BigQuery/Redshift） | 分析、聚合、看板 | 大范围扫描快，点更新弱，延迟秒到分钟级 |
| 时序库 | 指标、传感器 | 压缩率高、时间范围查询强 |

必说三个词：**索引**（读快写慢）、**复制**（读扩展、可用性、副本延迟）、**分片**（写扩展、分片键是命门、跨分片 JOIN 很痛）。

规范化 vs 反规范化：更新频繁就规范化，读远多于写就反规范化（并说清一致性由谁保证）。

### 2.2 缓存
- 放哪里：客户端 / CDN / API 侧（Redis、Memcached）/ DB 内部
- 策略：Cache-aside（最常用，未命中回源 DB）、Write-through（一致性优先）、Write-back（写快但有丢失风险）
- 该说的风险：**缓存失效**（TTL 或显式删除）、**惊群/Thundering herd**（并发未命中 → 加锁或提前刷新）、**热点 key**（复制或本地缓存）
- Redis 的其他用途：会话、限流、排行榜（Sorted Set）、分布式锁

### 2.3 消息队列 / 异步
- 用途：削峰、解耦、重试、扇出（一个事件多个消费者）
- 选型：SQS（简单、顺序弱）、Kafka（高吞吐、分区内有序、可重放）、RabbitMQ（路由灵活）
- 该说的设计点：**at-least-once → 幂等**（用处理 ID 去重）、**死信队列 DLQ**、**要顺序就用分区键**、**背压**

### 2.4 API 设计
- REST：资源导向、好缓存、对外 API 首选
- gRPC：内部服务间，类型安全、快、支持流式。浏览器直连不合适
- GraphQL：不同页面要不同形状数据时。问题是 N+1 和复杂度控制
- 顺口补一句：游标分页、幂等键、版本管理、限流

### 2.5 扩展性的套路
- 无状态 API + 负载均衡 → 水平扩展。会话放 Redis
- 读：副本 + 缓存 + CDN
- 写：队列 + 分片 + 批量化
- 重计算：拆到 worker（异步任务）
- 峰值：自动扩缩 + 队列 + 预热（Monoxer 的典型峰值是"上课开始时间、作业截止前"）

### 2.6 可靠性与一致性
- CAP/PACELC：网络分区时选 C 还是 A。按用途分开说："学习记录 A 优先、最终一致；计费、成绩确定 C 优先"
- 冗余：多可用区、健康检查、故障切换、熔断器、超时 + 重试（指数退避 + 抖动）
- 可观测性：指标（RED：Rate/Error/Duration）、日志、链路追踪、SLO 与告警

### 2.7 移动端 / 教育类容易被追问的点
- **离线支持**：端上本地库（SQLite）攒学习记录再同步。冲突用"服务器时间 + 端上生成 UUID"解决
- **推送通知**：APNs/FCM、token 管理、批量发送、发送时刻打散
- **未成年人个人信息**：按学校做租户隔离，权限（学生/家长/教师/校管理员），审计日志，加密
- **多租户**：共享库 + 所有表带 tenant_id + 行级安全；大客户可迁到专用分片

## 3. 数字小抄（只记数量级）

**延迟数字（Jeff Dean 版，约数）**
| 操作 | 时间 |
|---|---|
| L1 缓存访问 | 1 ns |
| L2 缓存访问 | 4 ns |
| 内存访问 | 100 ns |
| SSD 随机读 | 100 µs |
| 同机房网络往返 | 0.5 ms |
| HDD 寻道 | 10 ms |
| 内存顺序读 1 MB | 0.25 ms |
| SSD 顺序读 1 MB | 1 ms |
| 东京 ↔ 美国西海岸往返 | 约 100 ms |

**估算常用**
- 1 天 ≈ 86,400 秒 ≈ 10^5 秒。"DAU 100 万、每人每天 50 次请求 → 5×10^7/天 → 平均约 600 QPS，峰值按 5–10 倍算 3,000–6,000 QPS"
- 1 条记录 1 KB × 1 亿条 = 100 GB
- 单台关系库参考：写几千 QPS，读几万 QPS（配缓存）
- Redis：单节点 10 万 QPS 量级
- Kafka：加分区后百万 msg/s 量级

**可用性**
- 99.9% = 每月约 43 分钟停机，99.99% = 每月约 4 分钟

## 4. 三道例题（按 Monoxer 业务定制）

### 例题 A："请设计一个像 Monoxer 这样的记忆定着 App 的后端"

**澄清问题示例**
- 角色是否就学生 / 教师 / 校管理员三种
- 规模：导入学校几百到几千所，学生几十万到几百万，访问集中在上课时段
- 核心功能：课题（Book/Task）下发、出题、答题记录、按遗忘曲线算下次出题日、教师进度看板
- 是否需要离线学习、是否需要通知

**估算**
- 学生 100 万、每人每天 100 题 → 10^8 次答题/天 → 平均约 1,200 QPS，上课时段峰值 10 倍就是 1 万 QPS 以上的写入
- 一条答题记录 200 B → 每天 20 GB，一年 7 TB → 学习记录必须是追加写 + 分区

**高层架构**
- 客户端（iOS/Android/Web）→ CDN（静态资源、音频、图片）→ API Gateway/LB → API（无状态）
- 核心库（关系型）：学校、班级、用户、课题、题目（主数据，一致性优先）
- 学习记录（写入集中）：API → MQ（Kafka/SQS）→ worker → 追加型存储（按时间分区的关系库或 DynamoDB）
- 下次出题调度：Redis 存"学生 × 题目 → 下次到期时间"（Sorted Set 按到期取），持久化落 DB
- 教师看板：数据流进数仓（BigQuery），日级/准实时，聚合预计算（物化视图）

**数据模型（最少这些）**
- schools(id, name, plan) / classes(id, school_id) / users(id, role, school_id) / enrollments(user_id, class_id)
- books(id, owner_school_id) / questions(id, book_id, type, payload_json) / assignments(id, class_id, book_id, due_at)
- answers(id, user_id, question_id, answered_at, correct, latency_ms) —— 分区：answered_at 按月 + user_id 哈希
- memory_states(user_id, question_id, strength, next_due_at) —— 主键 (user_id, question_id)，next_due_at 建索引

**深挖时要讲的权衡**
- 答题是同步写库还是走 MQ 异步 → 体验上希望立刻显示"已保存"。API 投队列后直接返回 200，客户端乐观更新。失败重试 + 幂等键（client_answer_id）
- 遗忘曲线是否实时计算 → 出题时算好放 Redis，夜间批量重算
- 离线同步冲突 → 端上生成 UUID，服务端按时间戳合并，同一题重复以最后一次为准
- 多租户隔离 → tenant_id 列 + 应用层强制，大型补习机构可迁专用库
- 峰值 → 按课表预测自动扩容，队列吸收。明确说教师看板允许几分钟延迟

### 例题 B："每天早上 8 点给全体学生推送'今日课题'的系统"

- 需求：几百万条在 8:00 ± 几分钟内送达。不能重复、失败要重试、送达率可视
- 架构：调度器（cron/Cloud Scheduler）→"对象抽取任务"把 user_id 按 1 万一批切块投 MQ → worker 群并行调 FCM/APNs → 结果写结果表
- 权衡：把时间打散到 7:55–8:05 规避 API 限流 vs 用户期待"8 点整"。幂等用 (user_id, date) 做 key，Redis SETNX 判断是否已发
- 故障：worker 挂了 → MQ 可见性超时后重投。FCM 故障 → 熔断 + DLQ 事后补发

### 例题 C："用 LLM 自动生成题目、教师审核后发布的流水线"（往你的强项靠）

- 需求：教材文本（PDF）→ 候选题生成 → 质量检查 → 教师审核 → 发布。要控成本、延迟、质量
- 架构：上传 → OCR/结构化 → 切块 → 任务队列 → 生成 worker（调 LLM API，管理限流）→ 自动评估（规则 + LLM-as-a-Judge）→ 审核 UI → 通过后写入 questions 表
- 权衡：同步 vs 异步（要几分钟，必须异步 + 进度通知）、缓存（同一教材不重复生成：按输入哈希）、成本控制（批量 API、大小模型分工）、幻觉对策（必须附来源片段、人工审核为必经步骤）

## 5. 应对"偏硬件"的问题（过来人提到过）

能简短答出来就够。
- CPU 缓存和存储层级：L1/L2/L3 → 内存 → SSD → HDD。局部性重要，数组遍历比链表快的原因
- SSD vs HDD：随机 I/O 差 100 倍。为什么 DB 的索引设计和 WAL（追加写）有优势
- 网络：RTT 是大头。减少往返次数（批量、连接复用、HTTP/2）
- 线程与进程、上下文切换。I/O 密集用异步，CPU 密集用多进程
- 并发：锁、竞态、死锁，乐观锁 vs 悲观锁，用幂等让"重试安全"

## 6. 日语句型（直接套用）

**确认需求**
- 「まず要件を確認させてください。想定ユーザー数と、ピーク時のアクセス集中はどの程度でしょうか」（先确认需求：预计用户数和峰值集中程度）
- 「最初のリリースで必須の機能と、後回しにできる機能を分けてもよろしいですか」（能否区分首版必须和可以后做的功能）
- 「一貫性と可用性のどちらを優先すべきでしょうか。学習履歴は結果整合で良いと仮定します」（一致性和可用性优先哪个？我假设学习记录用最终一致）

**估算**
- 「ざっくり桁で見積もります。DAU 100 万、1 人 100 リクエストで 10 の 8 乗、平均 1,000 QPS 強、ピークは 10 倍を見込みます」

**设计判断**
- 「ここは RDB を選びます。理由は整合性と JOIN が必要なためです。代替として NoSQL も考えましたが、〜の点で今回は見送ります」（选 RDB，理由是需要一致性和 JOIN；也考虑过 NoSQL，因为某点放弃）
- 「書き込みが集中するので、API は即時応答してキューに積み、ワーカーで永続化します。トレードオフは数秒の遅延と冪等性の実装コストです」（写入集中，API 立即响应后进队列，worker 持久化；代价是几秒延迟和幂等实现成本）
- 「キャッシュを入れる場合、無効化のタイミングが課題になるので、TTL と明示的な削除を併用します」（加缓存的话失效时机是难点，TTL 和显式删除并用）

**卡住时**
- 「ここは仮定を置いて進めます。もし違っていればご指摘ください」（我先做假设推进，不对请指出）
- 「現時点で一番のボトルネックは〜です。規模が 10 倍になったら〜を導入します」（当前最大瓶颈是 X，规模 10 倍时引入 Y）

**收尾**
- 「まとめると、コアデータは RDB、書き込みはキューで非同期化、読み取りはキャッシュとレプリカで捌く構成です。弱点は〜で、次の一手は〜です」
