## 4. STAR ストーリー（1分〜1分半で話せるように。「チームで」ではなく「自分が」）

### STAR-1: LLM 評価基盤の構築（SoftBank）— 「評価基盤の構築」要件に直結
- **S**: 各事業部が RAG/エージェントを PoC していたが、精度の定義がバラバラで、本番化の判断ができなかった
- **T**: 横断で使える評価基盤と設計ガイドラインを作り、PoC → 本番の判断基準を統一する
- **A**: （自分が）評価データセットの作り方を定義（実業務ログからのサンプリング + アノテーション）、LLM-as-a-Judge と人手評価の相関を検証してから Judge を採用、Retrieval / Generation を分離して指標化、CI に組み込んで回帰検知
- **R**: 数値で語れるものを1つ用意（例: 評価工数の削減率、本番化した案件数、精度改善幅）。学び: 「唯一の正解」を Judge に求めすぎない（Stockmark の ACL 2026 論文と同じ問題意識、と結びつける）

### STAR-2: 金融ドメイン LLM + RAG 投資 QA の本番化（楽天証券）— 「研究成果のプロダクト化」
- **S**: 金融の専門用語・コンプライアンス制約の中で、投資に関する質問に答える QA を提供したい
- **T**: ハルシネーションを抑えつつ、根拠付きで回答する仕組みを GCP 上で本番運用
- **A**: ドメインデータでのファインチューニング、RAG のチャンク設計・メタデータ設計、根拠提示（エビデンス）と拒否ルール、レイテンシ・コストの設計、リリース後のモニタリング
- **R**: 本番提供に至った。学び: 金融でも製造でも「構造化されたデータと根拠提示」が信頼の前提 → Stockmark の「データ構造化」思想と一致

### STAR-3: Canlah.AI のマルチエージェント SaaS（兼業）— 「エージェントのワークフロー設計・評価」
- **S/T**: 少人数で K8s 上にマルチエージェントの SaaS を設計・運用
- **A**: エージェントの役割分割（planner / worker / verifier）、ツール呼び出しの失敗時のリトライ・フォールバック、状態管理、オブザーバビリティ（トレース）、コスト管理
- **R**: 本番運用中。学び: エージェントは「賢さ」より「失敗の扱い」と「評価可能性」で本番品質が決まる

## 5. 想定技術質問と回答の骨子

### エージェント設計
- **Q. エンタープライズ向けエージェントを設計するとき、何から決めるか**
  → 業務のゴールと「失敗したときに何が起きるか」から。ツールの権限境界、人間の確認ポイント（HITL）、状態の永続化、観測可能性。単一エージェント + 明示的ワークフローから始め、必要になってからマルチエージェント化。
- **Q. Agentic RAG と通常の RAG の違い、どこで効くか**
  → クエリ分解・複数回検索・検索結果の自己検証（エビデンスチェック）・不足時の再検索。効くのは「一発の検索で答えが揃わない」質問（横断比較、時系列、複数文書の統合）。コストとレイテンシが上がるので、まず「どの質問タイプで失敗しているか」を評価データで分類してから導入する。
- **Q. GraphRAG / ナレッジグラフをどう使うか**
  → エンティティ間の関係（製品—部品—不具合—対策など）を辿る質問に強い。抽出コストと更新運用が課題。まずはメタデータ + 構造化テーブルで代替できないかを検討。

### RAG / 日本語文書構造化
- **Q. ハルシネーションをどう減らすか**
  → 生成側より検索側に投資する。構造化（見出し・表・図面のキャプション・章構造）、チャンクの粒度、メタデータフィルタ、リランク、根拠の引用強制、答えられないときの拒否。谷本氏の「データ構造化の4つのポイント」の考え方に近い、と一言添えてもよい（読んだ上で）。
- **Q. 日本語の技術文書（PDF・図面・帳票）特有の難しさ**
  → レイアウト（縦書き・複数段組・表の結合セル）、専門用語・略語、OCR の誤り、同じ意味の表記ゆれ。Document AI / VLM での構造化と、辞書・正規化の併用。

### 評価
- **Q. LLM の出力をどう評価するか。LLM-as-a-Judge の限界は**
  → タスクごとに「正解が一意か」を先に見極める。一意でないタスクでは複数評価者の分布を見る（Stockmark の ACL 2026 論文の問題意識）。Judge は人手評価との相関を取ってから使う。Retrieval（Recall@k, MRR）と Generation（faithfulness, answer relevance）を分離。オンラインは人間のフィードバックと業務 KPI。
- **Q. PoC の成功をどう定義するか**
  → 精度の数字だけでなく「業務のどの判断が、誰の時間をどれだけ短縮するか」を先に顧客と合意する。初期価値検証は 2–4 週間、評価セットは顧客の実データから。

### PoC → 本番
- **Q. PoC 止まりになる原因と対策**
  → 原因: 評価が主観、データが本番と違う、運用者不在、コスト見積もりなし。対策: 最初から評価データと運用オーナーを決める、本番データのサブセットで PoC する、段階的リリース。
- **Q. 顧客要件をどう技術要件に落とすか**
  → 業務フローを一緒に書き出し、「AI が置き換える判断」と「人が残す判断」を分け、入力データの実物を早期に見る。曖昧な要件は仮説を自分で置いて、小さく検証して持ち帰る。

### モデル / 学習
- **Q. ファインチューニングと RAG の使い分け**
  → 知識の更新頻度が高い・根拠提示が必要 → RAG。文体・フォーマット・ドメインの言い回し・分類タスク → SFT。両方併用が多い。楽天証券の経験で具体例。
- **Q. 自社 LLM（Stockmark-2）と商用 API をどう使い分けるか（自分の意見）**
  → データ主権・オンプレ要件・コスト・レイテンシ・日本語品質。タスクごとにルーティング。評価基盤があれば切り替え判断ができる。

### 統計・ベイズ（歓迎要件、聞かれたら）
- 知っている範囲で正直に。A/B テストの検出力、信頼区間、少数サンプルでの評価の不確実性（ベイズ的に事前分布を置く考え方）程度は語れるようにしておく。

## 6. 強み・弱み

- 強み: 「評価 → 本番」までやり切る実装力とオーナーシップ。日中英で顧客・リサーチャー双方と話せる。
- 弱み（正直に + 克服策）: 論文執筆・学会発表の経験が少ない → Tech Blog・社内発信・リサーチャーとの共同で補う意欲。もう1つ候補: 大企業での標準化が長く、少人数での意思決定スピードは兼業で補ってきた。
