## 3. 前回評価された点を、榊原氏（構造化チーム）向けに再提示する

### 3-1. RAG を端から端まで作った経験（前回◎）
- 楽天証券: 顧客資産・市場データのパイプライン → リアルタイム RAG 知識基盤 → 金融 LLM のファインチューニング → GCP 上で API 化 → 24時間 QA。
- ソフトバンク: RAG／エージェントのリファレンス実装を標準化。インターン・若手向けの設計レビューも担当。
- 半年での進捗: Canlah.AI で 3 フレームワーク・10 以上のエージェントを契約レイヤー（共通エンベロープ、JSON スキーマ、タスク台帳ステートマシン）で統合し、K8s 上でマルチテナント SaaS として本番運用。

### 3-2. 「評価が難しいシステム」の評価（前回◎）
- LLM 出力と参照情報の整合性／忠実性を測る評価器を作り、人手評価で校正。複数 LLM の精度・コスト・実用性を比較してモデル選定とリリース判定に使った。
- VoC 分類: プロンプトと前処理の改善で Macro-F1 0.468 → 0.719。
- 話の持っていき方: 「評価基盤はリリース判定のためのもの」。Stockmark の ACL 2026 Industry 論文（LLM-as-a-Judge に唯一の正解を求めすぎていないか）に触れ、「評価の多様性」の話に繋げると榊原氏の隣のチームの話題になる。

### 3-3. ドキュメント構造化（前回「Excel 構造化で活躍できそう」）— ここを一番厚く
- ソフトバンク: RAG 前処理としての文書解析／OCR 基盤（文書分類、レイアウト解析、構造化出力）を開発・運用。8 名の OCR エンジニアリンググループで本番信頼性を共同担当。
- 具体的に語れる論点: 表・図面・帳票のレイアウトをどう扱うか、OCR 誤りを下流でどう吸収するか、構造化結果の評価をどう設計するか（正解データが不完全な場合）。
- Stockmark 側の題材: OmniDocBench-JASyn（日本語文書画像構造化ベンチ）、Stockmark-DocReasoner、Agentic OCR。「構造化の精度 = 検索精度 = ハルシネーション対策」という思想に同意し、自分の OCR 基盤経験を接続する。
